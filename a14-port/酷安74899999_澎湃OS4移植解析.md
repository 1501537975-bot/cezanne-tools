## 四、他是怎么做到的 —— 技术路线拆解

### 路线选择：移植，不是 GSI

```
源包：小米 17T Pro（warhol）澎湃OS4 OS4.0.0.10
  ↓ 移植到
目标：Redmi K30 Ultra（cezanne）
内核：4.14.357-perf-g2c5cc13（自编译，内置 KernelSU）
```

warhol 就是小米 17T Pro，澎湃OS4 基于 **Android 17**。所以这是**完整的跨机型移植**（改 device tree、vendor、overlay、重编内核），不是刷 GSI。

### 三个关键点

**① VNDK 保持 31，没有升 GKI**

`Vndk 信息 = 31` 意味着系统侧仍按 Android 12 的 VNDK 编译。这条路能走通，是因为：
- 系统包由**移植者重新编译**（ROM 作者署名 xiaochen & O.M.E.N），不是原厂包直刷；
- 重编时可以指定 `ro.vndk.version=31`、用对应 VNDK 的 apex、并在 system_ext 里放匹配的 `com.android.vndk.v3x.apex`；
- vendor 保留原厂（4.14 ABI 的 10 个 .ko 不重编）。

**② 内核用 4.14.357，不是原厂 4.14.186**

这是**最关键的差异**。4.14.357 来自 ACK `android-4.14-stable` 的较新 tag，相比原厂 4.14.186 包含了 **BPF 相关的大量上游修复**。

> 这正好解释了我之前判断的盲区：MTK 那个破坏 BPF arraymap 的 commit（ALPS05247589）在 4.14 早期 tag 里存在，**但后续 4.14-stable 会把它修掉**。升到 .357 就等于免费拿到了 BPF 修复，不需要 fake uname，也不需要手动回合补丁。

**③ EROFS 驱动必须自己 backport**

A17 的 system/product/system_ext 全是 erofs，而主线 EROFS 是 4.19 才有的，4.14.357 树里也没有。所以内核里必须有 `fs/erofs` —— 这正是 `LiaoWennian/cezanne-kernel` 已经做好的部分。

**④ BPF 与 EROFS 两个门槛的交叉验证**

| 门槛 | 他的解法 | 我们的现状 |
|---|---|---|
| EROFS 驱动 | 4.14.357 + fs/erofs backport | ✅ `LiaoWennian/cezanne-kernel` 已做 |
| BPF 修复 | 升到 4.14.357 顺带获得 | ❌ 我们用的是 4.14.186，**缺** |
| fake uname | **不需要**（真 4.14 也行） | 我之前误判为必需 |
| 内置 root | KernelSU | ✅ 我们有 `enable_ksu` 开关 |
| VNDK 31 兼容 | 移植者重编系统 + 配对 apex | 需要在移植步骤里做 |

## 五、这套方案对我们意味着什么

### 结论修正

我之前说「A15 以上必须 fake uname + BPF backport」——**不准确**。准确的说法是：

> **必须拿到 BPF 修复**。两条路：(a) 升内核到 4.14.357（他走的路）；(b) 留在 4.14.186 但回合 BPF 补丁 + 伪装 uname（`mt6873-dev` 那份内核走的路）。

### 推荐路线：以我们的仓库为底，合并 mt6873-dev 的 BPF 回合

`LiaoWennian/cezanne-kernel` 已经把最难的部分做完了（EROFS backport、GitHub Actions 流水线、原厂 defconfig、LOCALVERSION 对齐、AnyKernel3 打包、自检脚本）。**唯一缺的就是 BPF**。

而 `mt6873-dev/android_kernel_xiaomi_mt6885` 里正好有：
- `Import BPF Changes`（2025-08-02）
- `net: bpf, sockmap: convert to generic sk_msg interface`（2025-08-02）
- `Fake uname to 5.4.186 also for netbpfload/bpfloader/netd`（2025-08-02）

**两条路线可以合并**：

| 方案 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **A · 升内核到 4.14.357** | 合 ACK 4.14-stable 到 cezanne 树 | 改动大量符号 CRC，**必须重编全部 vendor 模块** | 高，需要完整 vendor 源码 |
| **B · 留在 4.14.186 + 回合 BPF** | 把 mt6873-dev 的 BPF 提交移植进我们的树 | 小，BPF 补丁本身不碰 vendor ABI | 中，但保留了原厂 10 个 .ko 可直接加载 |

**建议先走 B** —— 改动面小、可回滚、且我们已有的 LOCALVERSION 对齐设计（`4.14.186-perf-00252-g2f26b5917fd6`）正好保住了 vendor 模块的符号 CRC。加 fake uname 后兼容性最稳。

```bash

curl -sL "https://dl.coolapk.com/down?pn=com.coolapk.market&id=NDU5OQ&h=46bb9d98&from=from-web" -o ca.apk
python -c "
import sys; sys.path.insert(0,'camcp')
from coolapk_mcp.auth import libauth
libauth.save_blob(libauth.extract_blob_from_apk(r'C:\...\ca.apk'))"

# 2. 装 CLI
cd camcp && pip install -e .

# 3. 取帖（详情接口被验证码拦截时必须给 --uid 走作者动态列表回落）
```

- 详情接口返回 `captcha` 错误时，**必须提供 `--uid`**（作者 uid），工具会自动从作者动态列表回落
- 正文有「查看更多」截断，**关键信息几乎都在配图里** → 必须下图
- 图片 URL 去掉 `.xs` 后缀 = 原图；下载要完整浏览器 UA + `Referer: https://www.coolapk.com/feed/<id>`，间隔 4 秒防风控（HTTP 567）
